# Building the UI (25 Oct 2026): architecture, ownership, rules for the parallel tracks

The build of `UI_PLAN.md` / `UI_SPEC.json` (the decided design; nothing of it existed before this). This document
fixes what the parallel tracks share, so they cannot drift: the plumbing between the parts, who owns which files, the
rules that bind every track, how each verifies. Status lives in `..\HANDOFF.txt`; design in `UI_PLAN.md`; the spec in
`UI_SPEC.json` (mirrored by the mock-up, `..\tools\uimock\README.md`). Everything here obeys `..\CLAUDE.md` (the
guiding principles, no raw addresses, hooks chain, fails closed, the pre-change checklist) and `TESTING.md`.

## 1. Architecture in one picture
```
 FLvibed.dll (plain, global namespace)                 controller logic (flv_controller_impl)
 ┌──────────────────────────────────┐                  ┌──────────────────────────────────────────────┐
 │ core\flvibed.cpp  module switches│                  │ device.*   input-device service (pad / K&M)  │
 │ core\settings_bus.cpp  THE BUS   │◄── HostApi ─────►│ glyphs.*   glyph atlas, 3 families (own art) │
 │   [Modules] section registered   │ GetSettingsBus   │ uikit.*    row kit: panel, rows, focus, list │
 └──────────────────────────────────┘                  │ options_page.*  the FLVIBED page (5 tabs)    │
 controller host (flv_controller_host)                 │ padhud.*   badges, legend, status line, ...  │
 ┌──────────────────────────────────┐  OnUiButton      │ presets.*  FREELANCER / ACE / ASSISTED       │
 │ native buttons via 0x5A0C90:     │──────────────────►│ picker / wheel / goals / osk / newgame /    │
 │  bar button, options page button,│  OnRawKey        │ livesplit ... (phase D)                      │
 │  pause sixth button; page switch │◄─ SetUiButton ───│ + the registries: controller.cpp kOptions,   │
 │ LastRealKeyTick, RealMouseDown   │  UiButtonRect    │   autopilot_settings.cpp kDefs (register on  │
 └──────────────────────────────────┘                  │   the bus at Init, unregister at Shutdown)   │
 subtitles host: GetSettingsBus      subtitles logic:  │ core\ui_meta.h GENERATED from UI_SPEC.json   │
                                     registers kDefs   └──────────────────────────────────────────────┘
```
- **The settings bus** (`core\settings_bus.h`, one instance in FLvibed.dll): every module's `settings::Def` table
  registered with its section name, defaults, an `applied` callback and its ini writer. The options page reads rows,
  defaults and values from it and changes values through it (`Set` -> `settings::Apply` -> the owner's `applied`).
  No second copy of any value (UI_PLAN 1.2). `Generation()` lets caches refresh.
- **UI metadata** (`core\ui_meta.h`, GENERATED by `tools\ui_meta.py` from `docs\UI_SPEC.json`, committed; the drift
  check compares): per row key -> tab, section, label, kind (toggle / picker / slider / key / button), the picker words,
  slider min / max / step / unit / words, tier (player / advanced), needs (live / load / restart), parent, preset flag,
  help; the preset tables (autopilot, controller) and the bindings presets + shared situations (phase D). A row's
  registry key = its spec key; where the registry's key or value coding differs (e.g. spec `size` SMALL..HUGE over the
  registry's Int 0..4; `aim_mode` GIMBAL / RETICLE over Int 0 / 1), the generator's small alias table maps spec key ->
  (bus section, registry key, value map). **Keys the spec names and no registry has are NEW registry rows** (added to
  the owning module with type, range, default and a player-readable help line - `UI_PLAN.md` 3.4, the handoff's list).
- **The native buttons** are host-created (the game's factory, parented to the game's windows: the game's hit test,
  hover, click sound and click-vs-fire arbitration for free; UI_PLAN 2 / 3.1); the logic only draws over them
  (`UiButtonRect`) and gets their clicks (`OnUiButton`). The Options-screen page switch is host-side (the state byte
  the game uses; `OptionsPageState` / `ShowOptionsPage`); the logic draws the page in the panel area.
- **Drawing**: everything FLvibed draws goes through `core\game\render.*` (D3D8 text / box / sprite, survives Reset),
  placed through the UI camera (`ui::Project`, `render::ScreenSize`) so every resolution, aspect and DPI works as the
  subtitles' panels do; sizes as fractions of the screen height; fonts the game's own (`DATA\FONTS`, loaded FR_PRIVATE
  as `subtitles\src\impl\display.cpp` does - move that loader into `core\game\` so both modules share it). The HUD panel
  look (`display.cpp HudPanel`: base (13, 11, 26), frame line (118, 151, 180), bevel, chamfered corners, the scanline)
  becomes `core\game\uidraw.*` for the kit.
- **Input in the page and the pad screens**: pad through `Gamepad` (exists), keyboard through `OnRawKey` (host),
  mouse through the game's cursor position (`fl::MouseX/Y`) and `RealMouseDown`. Native actions only (clicks through
  `uiclick::Click`, maneuvers through the dispatcher, targets through `space::`), never cursor emulation (`..\CLAUDE.md`).
- **Glyphs**: drawn by FLvibed itself into the atlas (GDI shapes + letters: Xbox A B X Y coloured, PlayStation cross /
  circle / square / triangle, Nintendo B A Y X; bumpers, triggers, sticks, D-pad, View / Menu), so they are sharp at
  any resolution and need no asset, licence or download (`..\CLAUDE.md`: downloads need the user's OK; Kenney's CC0 set
  stays the later art swap, noted in the mock-up). Families by the pad's HID vendor id (Sony 054C, Nintendo 057E, else
  Xbox), overridable (`glyph_style`); confirm positional with the Nintendo swap (`confirm_button`).

Rules for sharing: a file outside your column is read-only for you - ask the orchestrator (your final report) for a
change there. `core\flexe.h` additions go through HOST only; another track that needs a symbol names it (address, what
for) in its report. `controller.cpp`: PAGE touches only the `Options` struct and the `kOptions` table, HUD everything
else. `api.h` is fixed (the orchestrator wrote v18 / v3); a track that needs more reports it. Build with
`tools\buildlock.ps1 dev` (one build at a time, machine-wide); a compile error in another track's half-edited file is
not yours to fix: wait a minute and rebuild. Commit only your own paths (`git add <paths>`), never `git add -A`, the
message in the repository's style, ending with `Co-Authored-By: Claude Fable 5.1 <noreply@anthropic.com>`.

## 3. Rules that bind every track (from the user; `..\CLAUDE.md`, `TESTING.md`, `UI_PLAN.md`)
1. **No raw addresses**: every hooked / called / read address is a signed symbol in `core\flexe.h` (signature from
   `build\sigtool\sigtool.exe gen <exe> code|data <va>`; `build.cmd sigtool` builds it). Vtable calls check the slot's
   target against a signed symbol. Read the disassembly (`tools\dis.ps1 <from> <to>`, `research\disasm\Freelancer.ann.asm`)
   before assuming an argument list; the game's own call sites show the arguments.
2. **Hooks chain** (the subtitles host already detours ManeuverLayout and CursorUpdate; HudShift / FLSharp hook the
   Options screen): `hk::Detour` follows an existing JMP. **Never change game logic**, never edit or ship a game file.
3. **Fails closed**: an unresolved symbol or an unexpected structure leaves the game's screen exactly as it is and
   logs which feature stays off; the settings stay reachable through the ini files and the debug commands.
4. **Every resolution, aspect and DPI**: nothing in pixels; fractions of H through the UI camera; verify at 4K and at
   1280x720 at least (the display matrix: `TESTING.md`, `kb\display.md`, `tools\fldata.ps1 Set-FLInstanceDisplay`).
5. **Native interaction** for the game's own controls and logic; FLvibed-drawn screens only where the spec draws them.
   Never cursor emulation for UI; the pad cursor option is FLvibed's own cursor driving the game's hit test natively.
6. **K&M untouched** except the autopilot's additions (the bar button, key K, the status line, the goal panel's mouse twin).
7. **Tests in the background** (`tools\deploy.ps1 -Background -Instance <n>`; HOST = instance 1, PAGE = 2, HUD = 3;
   phase D agents 4-6), the virtual pad (`Set-FLPad` / `Press-FLPad`), named controls, screenshots (`Save-FLShot`,
   `tools\flshots.ps1` sampler) + the live log read together; never a sound, never the user's screen; **close your game
   instance when done**. Hot-reload the logic with `deploy.ps1 -Impl -Instance <n>`; a host change needs a restart.
   Fixtures: `SaveC702` (space near Manhattan), `SaveC701` (docked), the main menu (no save). Judge by frames AND log.
8. **Write learned game facts into `docs\FREELANCER_RE.md`** (HOST) / `docs\kb` in the same commit; registry changes
   regenerate `docs\SETTINGS.md` (`tools\settings_table.ps1`); the mock-up order (`tools\uimock\README.md`): a UI change
   that deviates from `UI_SPEC.json` is reported to the orchestrator, who patches the mock-up and the spec.
9. **Settings**: every new behaviour is a registry row with a sane default and a player-readable help line; names =
   the spec's keys; defaults = the spec's `def`.
10. **Report** at the end: what works (verified how: instance, save, screenshot paths, log lines), what does not, every
    deviation from the spec, every request to another track (symbols, API, files), the commits made.
