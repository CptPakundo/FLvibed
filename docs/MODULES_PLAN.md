The autopilot is the most contained large cluster. `autopilot_impl.h` leaks into five outside files (goals, hud2,
mprules, padhud, picker).

Findings that decide the architecture:
1. **Core has no runtime.** It is a library compiled into each part plus two buses (`settings_bus`, `hud_bus`). The options
   page lives in the controller logic, which is why `controller = 0` has no options page (open since 0.2.x).
2. **Shared state is the trap.** `core\game` is compiled into each logic part, so each part has its own copy of every
   static. That is harmless with two parts that hardly share. Split HUD, Pad and Autopilot the same way and they would read
   each other's game state as silently stale. **`core\game` must become one instance before any split.** Of 293 statics
   examined, 281 are safe to merge; the 12 that are not are listed under P1.
3. Not a problem, checked: signature verification costs 0.2-0.3 ms per part; `core\` has no per-module `#ifdef`s; no tool
   parses the 30 `Log` lines in `core\game`.
4. **Hooks are duplicated and misplaced.** Both hosts hook `FrameUpdate`, device Reset and CreateDevice (the source of the
   open "re-patch ping-pong"). Borderless windowed (`winmode`) and the input injection sit in the controller host, so the
   autopilot and the window mode die with `controller = 0`, and K&M autopilot needs the pad module loaded.
5. The bus idiom is proven: plain structs, published per frame, stale = absent, fails closed. Subtitles already work this
   way against HUD 2. Generalise it instead of inventing a framework.
6. **The hub holds services, not only calls.** `controller.cpp` advances the game clock (:2564), runs `ai::Update` (:2612), detects
   the game mode and fills `uiopt`. `fl::` (the key commands and game state: about 200 autopilot references) and `events::` (358) sit
   in the controller too. These must reach core before any cut that needs them, not when the hub finally dissolves.
7. **The autopilot's output is pad intent, not commands.** `if (UpdateAutopilot(dt)) return;` is an early return in the middle of
   `UpdateSpace` (:2348), and the frame OR-merges autopilot output with the pad's held actions (:1829, :1868). No priority table
   exists to move. This has to be untangled in place first.
8. Path dependence: about 200 tracked files name the source paths (69 `.md`, 16 `.ps1`, 8 `.json`, hooks and research `Watch:`
   lines). Moves need a scripted rewrite, not hand edits.

**"Did I miss a module?"** Two, both above and approved. **Display:** a player-facing feature living inside the pad module for no
reason. **Speedrun:** cleanly separable (22 references) and useful without a pad. Considered and rejected as modules:
*Multiplayer* (the client side is a 189-line rule reader that several modules consult: a core service; the plugin stays in
`server\`), *the harness* (every module has commands, so the transport is a core service and each module registers its own),
*Extended HUD 2* (a HUD part with its existing `ui_style` switch), *haptics and cues* (parts of Controller and HUD).

**Rules that make it hold:**
- **Still one DLL**, static runtime, no new prerequisite, `dacom.ini` unchanged. A module is a namespace, a folder and a
  switch, not a file.
- **Two layers, the same in dev and release.** Host (`FLvibed.dll`): hooks and buses. Logic: `core\game` once, then every
  module in its own namespace; `FLvibedLogic.dll` in dev, linked in for release. Dev keeps hot reload, as one reload of all
  logic instead of per module. Accepted because a dev build shaped differently from release would hide exactly the state
  bugs of finding 2.
- **Dependencies point one way:** module -> core. A module never includes another module's headers. Module to module runs
  through a core bus (a published read-only view, or a command); a missing publisher is stale = absent = classic behaviour.
  The namespace makes a violation fail to link; `tools\module_lint` also makes it a named check.
- **A hook used by two or more modules lives in core** and dispatches in a fixed table; a hook one module needs stays in that
  module's host part and installs only when the module is on. A module that is off installs nothing.
- **One frame order, written down.** The router's table reproduces today's order exactly, traced, not assumed. Subtitles start
  first, but a later detour chains in front of the earlier one and both act before calling the original, so the controller's frame
  runs first and the subtitles' second (from the code; the fingerprint's hook table confirms it). Three event classes, because
  they differ today: the frame, the modal loop's frame (the controller only, `main.cpp:500`) and each draw pass.
- **A fault stops one module.** Today a fault disables one logic and the other plays on. The router keeps one fault flag and one
  fail-safe per module (held keys, steering and cursor released, as `HostFailSafe` does), so one logic DLL does not become one
  point of failure.
- **Held commands have owners.** `Hold`, `Tap` and `ReleaseAll` become core services keyed by module, so one module's release
  never drops another's holds.
- **Nothing player-facing moves:** ini files and sections (`FLController.ini`, `[Controller]`, `[Autopilot]`, ...), keys and
  defaults, log names, `EXE\FLSubtitles\`, shm channel names, `deploy -Modules` old values. A section may have several owners
  (the settings bus refuses that today: it gains it in P3), because `[Controller]` holds HUD, speedrun and window rows.
- **`[Modules]` migration:** a new row that is absent inherits: hud, autopilot, speedrun, display and npc from `controller`, movies
  from `subtitles`. A row that is present wins, so "HUD without Controller" is `controller = 0`, `hud = 1`. The save writes only rows the
  player changed, or the first save would freeze inherited zeros. Today both switches at 0 means no hooks at all: that troubleshooting
  state stays as `safe = 1`, which installs nothing.

**Folders:** each module moves to `modules\<name>\{src, docs, tools, data, CLAUDE.md}` at its own cut, because `build.cmd` globs
folders and a module's namespace follows its folder; the scripted path rewrite runs after each cut. `core\` stays; the harness (`controller\tools\flctl*`,
`flsweep`, `flleg`) moves to a new harness folder under tools, `HARNESS.md` to `docs\`. Module-owned docs move with the module (`UI_HUD2*` to
HUD, `AUTOPILOT*` to Autopilot). `docs\` keeps what is about the game or the whole project.

## 3. How regressions are kept out
A refactor proves itself by **nothing changing**, so most of the proof is cheap and needs no game.

**The freeze: fingerprints taken in P0 at HEAD, compared after every package.** A difference is explained or is a bug.
| Fingerprint | Catches | Cost |
|---|---|---|
| `docs\SETTINGS.md` regenerated, every key / default / help | a lost or changed setting | seconds |
| `ui_meta.h`, the options page's rows | options drift | seconds |
| hook table from one game start: detours, vtable and import patches, chain order | a lost or reordered hook | one start |
| frame and draw order (`order:` in `perf cpu`) | event order drift | one start |
| debug command inventory | harness breakage | one start |
| `build.cmd test`, dev and release builds, `win7_check` | logic, imports | under 2 min |
| `perf cpu` over a fixed fixture | Efficiency: per-frame cost, HUD 0.3 ms budget | one fixture |
| release DLL size | core really is one instance | free |

**In game, by reach** (Working method 4, 23): each package states its budget and runs only the sweep sections its cut can
touch. **New sweep section `modules-matrix`:** all on, core only, each module alone, each module off, plus the owner's named
cases (Controller without HUD, Subtitles without HUD, Autopilot on K&M without Controller); a start, a flight, a dock, the
options page, ~40 s per configuration over 3 games.

**The full sweep and the leg gate run only on the owner's word.** Recommended twice: once at HEAD as the baseline, once at

**Reading:** the +5 us was the load: on a quiet machine P1 is level with the baseline. P2 reads 1.7 us under it, but one build spreads up to 3.8 us between launches, so three rounds tell neither that nor a cost of about 1 % from zero: what they show is no cost above that noise, and `OnFrame` nowhere near the 15 % mark. Round 3's subtitles 37.9 is a phase of the fixture falling inside a span (a line on screen), not cost. "Quiet" means the rest of the machine under 3 cores, not idle.

**The guard:** `tools\fingerprint.ps1` measures the rest of the machine during each span (all CPU time but the game's and its own, in cores, `machine:` lines in `spans.info`). A span above `-QuietCores` (3.0; a quiet sample read 1.8-2.7 cores, a busy one 4.5-11) throws the launch away, because a retried span would sit later in the fixture; it then waits for calm and starts again, for at most `-QuietWaitMin`, and otherwise exits 2 with no perf file stored. Generic: it names no process. Frame orders are not cost and stay in `orders.info` either way.

since each package compares with the one before. So **every package also runs `-Compare <p> -Against baseline` and reads the perf rows:

always exits 1 on `ui_meta.txt` (above): the perf rows are what it is for. Also watch for a repeat of the start that died at D3D creation:
a second one is a bug to chase, not noise.

The autopilot's packages also use `tools\apdiff.py` (archived leg runs compared as structure).

## 5. The audit, without reading anything twice
Reading all source once is about 1.4M tokens and all docs about 1.2M. The audit's cost is decided by how often that happens,
so the rule is **each file is read once, when it is already being moved**:
- **At each cut (P5-P9):** one audit agent per module, read-only, reports `finding - path:line - severity - proposed check`
  under 4 KB: guiding principles, the architecture of the module, legibility, comment quality, carried rows of
  `..\AUDIT_2026-10-31.md`. Routed by the private routing policy: `code-review` for code, `docs-audit` for docs. Claims are
  verified before they enter (Working method 10). The fixes are a separate commit from the moves, so a move stays a pure move.
- **Comments:** a standard first (`docs\COMMENTS.md`: a header on every file; say what and why; no dated narrative, version history or owner quotes
  in code: those belong to the docs and git), checked by a lint. Rewrite by hand only the module headers, public APIs and the
  20 largest files; the rest improves when touched. A whole-tree comment rewrite is not worth its tokens or its diff noise.
- **Giant files** (`autopilot_combat.cpp` 310 KB, `display.cpp` 224 KB, `autopilot_objective.cpp` 216 KB, `controller.cpp`
  170 KB, `hud2.cpp` 144 KB): split by responsibility in pure-move commits after their cut.
- **Docs (P11, parallel and cheap, no builds):** `tools\docindex.py` and `docrefs.py` first (the machine finds dead links and
  orphans for free), then agents only on what they flag: stale mentions, dated state in CLAUDE.md maps (rows C1, C2, C6-C8),
  `docs\research\player-ship-ai.md` against `docs\research\npc-ai.md`, oldest-untouched docs (17-19 Oct). Facts stay; narrative
  goes to history. Every repeated finding becomes a check, not a sentence (Working method 16).

One wave never exceeds 8 agents. Agents read and report; they never build or run games. Bulk findings stay in files, not the
driver's context.
